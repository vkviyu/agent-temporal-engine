# R14 Agent 准备增长基线

日期：2026-11-17。R14 已完成基线测量，mutation-delta 明确延期，不接入 canonical
production path。

## 测量范围

新增 `engine/agent_prepare_growth_benchmark_test.go`，复用现有
`workImageFixture`，以 16、128、4000 groups 测量 64、512、16000 条初始 record
下的单 Agent 命令、Work uncached、Work warm 和后段 reducer failure。

fixture 使用内存编码对象源，排除 admission、journal publication、fsync、真实文件
IO 和进程峰值 RSS。指标区分 `RecordImage.Size()`、record 数量、record-root envelope、
源对象读取、读取字节、builder object 字节和 `storage.PreparedTransaction.Size()`。
原有 `profile-B` 已改名为 `root-envelope-B`，避免把根描述符误解为完整状态大小。

## 命令与结果

```sh
go test ./engine -run '^$' \
  -bench '^BenchmarkR14AgentPrepareGrowth$' \
  -benchmem -benchtime=100ms -count=3 -cpu=1 -timeout=12m
```

命令通过，环境为 Go 1.27.0、Darwin/arm64、Apple M1。代表范围：

- 64 records：单命令约 1.8–2.8 ms、约 1.9 MiB 累计分配。
- 512 records：单命令约 14.1–19.2 ms、约 14.7 MiB 累计分配。
- 16000 records：单命令约 0.40–0.42 s、约 450 MiB 累计分配。
- 16000 records 的 Work uncached 约 2.94–6.80 s、约 3.15 GiB 累计分配。
- 同规模 Work warm 约 0.87–1.04 s、约 0.99 GiB 累计分配；后段失败约
  0.81–0.85 s、约 1.02 GiB 累计分配，且没有产生提交计划或事务字节。

这些是 `testing.B` 的累计 `B/op`，不是峰值内存；时间波动来自共享开发机。
对象读取和读取字节已作为 benchmark 指标输出。没有用历史 legacy 对照，也没有
新增旧格式 reader。

## 决定与限制

结果表明当前全量 record image 准备是明显的增长成本，但当前架构不适合直接把
mutation-delta 接入生产路径。`ApplyCommandRecords` 依赖完整 candidate clone、
canonical record image 编解码、跨记录关系校验和 Restore；record key 还由
`SHA256(raw)+duplicate ordinal` 构成。Ledger 没有足够的 lifecycle/Recovery 反向索引，
Work cache 也只保存 immutable image/catalog。绕过这些步骤会破坏失败隔离、规范化或
恢复等价性。

因此本项明确延期 production mutation-delta，保留全量 `ApplyCommandRecords` 作为唯一
语义 authority，不新增第二份 Ledger、旧 snapshot cache 或不完整 changed-record
持久化入口。未来若重新启动，必须先实现不改变生产路径的 shadow delta，并证明
Result、Snapshot、canonical records、RecordKeys、Size、StateOps、receipt、RootSet、
transaction bytes、reopen/full replay 和 Work failure isolation 全部等价；同时证明
新增关系索引成本低于节省的 clone/encode/validation 成本。真实文件 IO、峰值 RSS 和
发布成本另属后续测量。
