# R23 adapter 锁内 IO 第一阶段基线验证

日期：2026-11-18。本阶段检查 `journalstore`、`graphstore` adapter 的锁覆盖、
publication IO、StateReader 调用、Close/reopen/cancel 和 callback 边界。目标是
确认是否存在可以安全缩短总锁范围的明确收益；没有修改 production adapter 或
storage Journal path，也不提交 Git。

## 当前锁边界

底层 `storage.Journal` 已经把两类职责分开：

- `Journal.mu` 只捕获 publication、layout、pin 和 active reader 状态。实际
  `ReadAt` 在锁外执行；`PinnedReader` 也在锁外执行文件 IO。
- `writerMu` 串行化 publication、checkpoint、compaction、retirement 和 Close。
  它跨物理 IO 是单 writer ownership 契约，不能仅凭耗时将其视为错误。

adapter 层仍然更粗：

- `journalstore.Store.mu` 覆盖 `Journal.PublishWithRecords`、`Journal.ReadAt`、
  projection callback、receipt/index 安装以及 `Close`。
- `journalstore.RecordsPage` 和 `ReadRecords` 在 `Store.mu` 内执行 journal
  `ReadAt`，因此慢读会阻塞 Lookup、Append 和 Close。
- `graphstore.Store.mu` 覆盖 `graph.VerifyState` 的外部 `StateReader.ReadEntries`、
  `Journal.PublishWithRecords`、graph projection 安装和 `Close`。
- 两个 adapter 的 callback 注释都禁止 callback 重入 Store；在当前不可重入
  `sync.Mutex` 下，重入 Lookup、Read、Append 或 Close 会等待同一把锁。

Engine 主路径已有更细的边界：public read 只在 `e.mu` 内捕获 roots/read cut，
P1 IO 通过 writer gate 串行化，但不把核心 `e.mu` 跨 IO 持有。R23 的问题集中在
实验性 adapter，不代表 Engine coordinator 的 writer-lock 设计需要回退。

## 新增基线

新增：

- `journalstore/r23_adapter_lock_test.go`
- `graphstore/r23_adapter_lock_test.go`

`TestR23AppendHoldsAdapterLockAcrossPublicationIO` 使用 test-only `SyncDir`
gate，在 journalstore publication 的目录同步阶段暂停 Append，再尝试 Lookup。
Lookup 在 gate 释放前必须保持阻塞，释放后必须看到同一份 durable receipt。

`TestR23AddRevisionHoldsAdapterLockAcrossStateReader` 使用 test-only blocking
`StateReader`，在 graphstore `AddRevision` 的 state verification 阶段暂停，再
尝试 `Get`。Get 在 StateReader 释放前必须保持阻塞，释放后必须返回正常的
unknown-revision 结果。

这些测试证明的是当前锁覆盖和可观察阻塞关系，不把阻塞时间伪装成设备 IO
统计，也不宣称 adapter 存在数据一致性错误。

## 正确性证据

已有 Engine writer-lock 回归继续覆盖更高层边界：

- `TestCoordinatorPlanningIOReleasesCoreAndHonorsConcurrentFence`
- `TestCoordinatorP1ReleasesCoreAndClosesOldPolicyOutput`
- `TestCoordinatorCompletionDoesNotNestAdmissionAndCoreLocks`
- `TestWriterGateSerializesMaintenanceAndCloseWithP1`

已有 storage replay/callback 回归覆盖 callback 的 borrowed reader 生命周期、
publication prefix 限制、callback failure 在 tail repair 前返回，以及最终认证
失败不能 Ready。

本阶段新增的两个 R23 adapter 基线测试均通过。没有发现 callback 重入后可以
安全继续执行的现有契约；当前文档已经明确 callback 不得重入 Store。

## 当前判断

R23 以“基线完成、保留当前 adapter 锁边界”收口：

- adapter 总锁确实会跨慢 IO 和外部 StateReader/callback，存在并发读写被串行化
  的结构成本。
- 直接释放 adapter 锁会暴露 candidate projection、receipt/index 安装、未知
  publication outcome 和 callback 重入问题，不能作为局部优化。
- 安全拆分需要新的 private staging、publication ownership、callback isolation
  和 Close/cancel 契约，并且要有真实 workload 的等待比例证据。
- 当前 evidence 只有锁覆盖基线，没有证明拆锁收益足以承担语义重构成本，因此
  本阶段不修改 production path。

后续若重新开启 R23，应先增加可注入的 adapter IO/callback phase timing，分别
测量 journal publication、record read、StateReader verification 和 Close 等待
占比，再设计不暴露 private projection 的锁外执行方案。

## 验证范围
