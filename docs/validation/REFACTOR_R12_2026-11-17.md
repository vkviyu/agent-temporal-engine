**当前结论：R12 在本文界定的代表场景与分层验证范围内已达成计划验收。** 初次核对发现的两个阻塞缺口已经补齐：真实 Store durable commit 后丢 ACK 的 unknown/重连 receipt/retry 闭环，以及公共 content 输出预算的 embedded/pipe/unix 对照。三包普通/race 均通过；定向 `-v` 明确确认 9 组共享场景的 pipe/unix 子测试和 3 项独立 Unix 测试均 PASS、无 SKIP。当前结论不追认先前批次的未知 skip 状态，也不声称具备统一 manifest、工作树 fingerprint 或全库验证证据。

## 1. 验收依据与比较口径

[主计划 R12](/Users/zhaozhiqiang/work/agent-temporal-engine/docs/ATE_REFACTOR_MASTER_PLAN.md:258) 要求：

> 统一场景 corpus，分别接入 embedded facade、真实 Unix service/client，以及适合协议边界的 net.Pipe harness。复用已有 service/client 测试，不强迫只在真实 Unix 上成立的身份/权限场景运行于 net.Pipe。
>
> 同一命令的 receipt、错误类别、historical anchor、分页、撤回和超大结果行为一致；额外覆盖 session principal 绑定、foreign view、一次性 grant、取消、断连、未知提交重试。使用能力矩阵标记不适用场景。

实际 harness 位于 [work_summary_emission_test.go](/Users/zhaozhiqiang/work/agent-temporal-engine/service/work_summary_emission_test.go:365)：

- `conformanceClients` 的 pipe 路径使用 `net.Pipe`、真实 `Server.acceptConn` 和 `client.New`；unix 路径使用 `Server.Listen`、`Serve` 和 `client.Dial`，不是用 pipe 冒充 Unix。
- 每个 transport 子测试创建自己的真实 `*ate.Store`；同一子测试内，embedded 与 SDK 共享该 Store。首次命令与原键重试可从不同入口进入，比较同一次 publication 的完整 `CommitResult`，避免独立 StoreID/digest 不可比。不是三个独立数据库之间的确定性证明。
- `assertReadEqual` 对成功结果做 `reflect.DeepEqual`；失败场景另以 `remoteCode` 对照 `core.ClassifyError(localErr)`。未使用该对照的错误断言，不能自动记为三端错误类别一致。
- `OpenView` 两次产生不同 handle，只比较相同 cut 的 Anchor/ViewDigest，并分别用各自 handle 读取。连接 ownership 是服务附加契约，不能要求 embedded 的 handle 使用方式与远程 session 相同。
- [domain_test.go 的 `orderedMemoryResult`](/Users/zhaozhiqiang/work/agent-temporal-engine/service/domain_test.go:273) 仅规范化无序集合的顺序，保留所有记录及 proof 字段；不对有序分页结果排序。

**本轮实现的两类补充：**

1. **真实提交后的 ACK 丢失与原键重试（S13）。** `r12LostACKConn` 透传 hello，随后读取并保留真实服务返回的整个 mutation response，向 SDK 返回 EOF 而不交付任何 ACK header/body，并关闭底层连接。测试解码被丢弃的 response，要求无协议错误且是 `CodeDurableAck`，LSN 恰比写前增加一次，Store snapshot 的 Fence/RootSet 与 receipt 一致。这是确定性的 SDK 交付边界故障，不是伪造 backend 结果，也不是模拟磁盘提交失败。SDK 必须返回零 CommitResult 与带原认证 RequestKey 的 `OutcomeUnknownError`。新连接使用相同 token 查询 receipt，与 embedded lookup 完整相等；SDK 与 embedded 分别重试同一请求，包括仍指向写前 cut 的 `ExpectedFence`，必须返回原 receipt。每一步核对完整 StateSnapshot 不推进，最后比较状态值。未使用 sleep 或概率性断连，也未测试进程 crash/reopen。
2. **真实 Store 上共享读取预算的成功/拒绝对照（S14）。** 使用 16 KiB 二进制对象，embedded 与 SDK 各自打开 owned View 并比较 cut；offset=5、length=8192、MaxBytes=64 KiB 时结果与精确原字节一致。随后仅把 MaxBytes 降至合法的 4096；先检查成功结果的 JSON 确实超过此预算，避免误测非法参数。embedded 分类与远程错误均为 `ErrorResourceLimit`，两个返回值都是零 ContentRange。保持同一 SDK、view、offset 与 4096 预算，将 length 改为 32 后成功读取并做差分，完整 publication 不变。依据现有 [ReadContent 输出预算检查](/Users/zhaozhiqiang/work/agent-temporal-engine/engine/node_content.go:102)，没有添加新的限制或改变协议 frame ceiling。
