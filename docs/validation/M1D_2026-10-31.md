## 审计发现与修复

1. **候选状态拒绝过早返回。** A 的候选 put 可能让 B 的 ConditionAbsent 失败，旧实现会在 A 发布前向 B 返回冲突。若 A 随后写入失败，B 的结论来自未发布状态。现在依赖批内候选的拒绝延迟到 P1 成功；P1 unknown 时 B 返回 StoreFenced，不泄露候选结论。明确未开始写的发布拒绝会让这些请求回到 FIFO 重验。
2. **完成窗口与 admission 计费。** 发布成功后的 hint/fence 更新和全部 flight 完成现在处于同一个 admission 临界区，避免已提交键仍因 alias waiter 限额被拒；完成时释放 owned Body/Fence，取消最后 waiter 不提前释放尚未完成命令的配额。
3. **多事务尾部隔离上限。** recovery 以合法 prepared batch 上限约束未发布尾部，不再使用可能更小的自定义单事务限额；保留 published-only 认证边界。
4. **版本断言维护。** CLI usage 测试中的旧 M1c 字符串在版本更新时暴露失败，已移除与 usage 无关的阶段断言；版本输出仍由专门的 main 测试验证。

## Go 库与 CLI 并发往返

实际使用根包 `ate.Create`，配置 `MaxCount=8`、`MaxDelay=1s`，8 个 goroutine 同时提交 8 个不同 RequestKey 的 Mutate，各写一个不同键：

1. 全部收到 Ack；全局 Snapshot 为 LSN=8。
2. Close/Open 后，对每个 RequestKey 的 LookupResult 与原 Ack 全字段相同，8 个值均相同，成员自己的 LSN 共 8 个。
3. 物理 publication Generation=1：8 笔事务经过一次 P1，成员仍保留各自 proof。
4. 再次 Close 后执行 `recover-state DIR`：`semantic_replay_verified=true`、generation=1、last_lsn=8，RootSet 与库 Snapshot 相同。

最终实例 RootSet 为 `bfd96f9475b1ec2292e56ba459fb1f0c8bf39108b33593aa57fb1c401b731d7a`。事务含随机 TxID，RootSet 不是跨运行固定 golden；验收依据是同一次运行的原 Ack、重开 Lookup、Snapshot 与 CLI 恢复严格一致。

## 范围与结论

M1d 验证的是进程内接受/等待边界和整批持久发布的正确性。InFlight 不是 durable admission token；进程在 P1 前退出可能丢失队列，必须用原 RequestKey 的 verified receipt 或 NotFoundAtFence 对账。未测量吞吐/尾延迟，也没有设备断电认证。
