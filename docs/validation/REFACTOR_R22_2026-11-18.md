# R22 compaction/checkpoint/replay 第一阶段基线验证

日期：2026-11-18。本阶段测量 AuditFull compaction、recovery checkpoint、完整
semantic replay、checkpoint suffix replay 以及 compaction 后 reopen 的维护成本。
目标是先建立可复现基线，再判断哪些物理验证或 replay proof 可能安全复用。
本阶段没有修改 production compaction、checkpoint、replay 或 publication path，
也不提交 Git。

## 范围和测量口径

- 新增 `engine/r22_maintenance_benchmark_test.go`，通过公开
  `engine.Create`、`Mutate`、`CreateRecoveryCheckpoint`、`CompactAuditFull` 和
  `OpenExisting` 构造真实 Directory Engine fixture。
- fixture 覆盖 core-only 和 `AgentProfile` + `EventProfile` 两种路径。状态始终
  写入同一个 `r22-key`，使逻辑 state 有界；事务 request ID 和 payload 仍然变化，
  用于增长物理 journal history。
- `BenchmarkR22OpenFullReplay` 测量禁用 checkpoint 后的完整 physical scan 和
  semantic replay。
- `BenchmarkR22OpenCheckpointSuffix` 测量已有 checkpoint、追加 suffix 后的 warm
  open，观察认证、物理扫描和 suffix replay 的关系。
- `BenchmarkR22CreateRecoveryCheckpoint` 测量 recovery checkpoint 创建总耗时。
- `BenchmarkR22CompactAuditFull` 测量 AuditFull compaction 总耗时、复制的
  logical frame bytes 和 retired segment count。
- `BenchmarkR22OpenCheckpointAfterCompaction` 测量 compaction 后 checkpoint
  coverage 仍然有效时的 warm open。
- `BenchmarkR22OpenFullReplayAfterCompaction` 在 compaction 后禁用 checkpoint，
  用于确认完整历史仍然可以重新 replay。
- benchmark fixture 的有效规模为 16、64、128 records。256 和 1024 规模的
  校准在 fixture 构造阶段触发 `journal resource limit exceeded`，没有进入
  maintenance measurement，因而不属于正式结果。
- `B/op` 和 `allocs/op` 是 benchmark 生命周期内的累计分配指标，不是峰值 heap
  或 RSS。
- `Compaction.Bytes` 只表示 observation 记录的 copied logical frame bytes，
  不表示设备写入总量。
- `Open.Bytes` 表示 published prefix bytes，不表示设备 read bytes。
- `maintenance-count` 表示 observation 中的维护计数，在 compaction 基准中对应
  retired segment count，不是完整 IO 次数。
- checkpoint observation 当前只提供总 Duration/Outcome，没有 source physical
  verification、prefix hashing、projection validation、checkpoint write/sync、
  target verification、publication install 和 cleanup 的独立计数或时长。
- 不能从总 benchmark 时间或重叠的 Read/Scan 事件反推出上述阶段的设备 IO、
  fsync latency、page cache 命中率或各阶段占比。

## 校准边界和失败样本

最初的 256/1024 fixture 使用不同 key，导致 reducer state image 随历史增长，
在约 156 个事务处触发：

```text
journal resource limit exceeded
```

fixture 随后改为重复更新同一个 key，以隔离逻辑 state 增长和 transaction
history 增长。即使使用单一 key，256/1024 仍在约 126–197 个事务之间触发当前
journal frame/resource limit。两次失败校准中，失败位置随 core/profile 路径和
运行波动变化，但都发生在维护操作开始之前的 fixture 构造阶段。

因此本阶段没有扩大 production journal/frame 上限，也没有把 256/1024 硬塞入
R22。16/64/128 是当前存储边界下能够完整执行全部维护路径的有效测量范围；
更大历史增长属于 R14/R24 的独立容量问题。

## 当前判断

当前证据支持以下判断：

- checkpoint warm open 仍执行完整物理扫描和认证，但只 replay checkpoint
  coverage 之后的 suffix。`certified` 和 `scanned` 保持完整历史计数，而
  `replayed` 对应剩余 suffix。
- compaction 后 warm open 的 `replayed=0`，说明 checkpoint coverage 在新的
  published layout 上仍然有效；compaction 没有破坏 checkpoint、历史 receipt 或
  publication 语义。
- compaction 后禁用 checkpoint 会重新 replay 全部事务，说明 checkpoint 是
  加速恢复的认证投影，不是完整历史的替代品。
- profile fixture 的 full replay 和维护成本高于 core-only，且累计分配随有效
  history 增长明显。这个结果支持后续 R14/R24 继续研究 reducer image、checkpoint
  projection 和峰值内存预算，但不能直接推出 RSS 或峰值 heap。
- compaction copied bytes 随 published logical history 增长，说明 AuditFull
  compaction 当前仍复制完整 logical frame stream；本阶段没有证明可以安全跳过
  source verification、target verification 或 publication recheck。
- Engine compaction/checkpoint 各自使用 fresh verifier；storage 仍保留最终
  publication 和物理认证边界。当前 observation 不能把重复成本拆成可复用 proof
  与必须保留的 authority check。

本阶段不引入 proof reuse，也不新增 production tracing。若后续继续优化，应先
增加 test-only IO/phase wrapper，分别记录 source verification、semantic replay、
prefix hash、projection validation、checkpoint sync、target verification、install
和 retired cleanup。只有获得阶段占比和正确性对照后，才判断是否存在不改变最终
authority 的安全复用边界。
