# R24 历史索引、cache 与恢复内存第一阶段基线验证

日期：2026-11-18。本阶段区分 durable authority、可重建历史索引、bounded
cache、checkpoint projection 和请求/Work 私有状态，并测量现有 TaskTrace 与
Agent prepare 路径的累计分配和结构字节。没有把 B/op、fixture bytes 或
RetainedEstimate 解释成峰值 RSS，也没有修改 production cache、index 或
reducer path。

## 对象分类

当前对象边界如下：

- 已发布 journal、RootSet、receipt、event/object records 和 domain/agent/
  knowledge roots 是 durable authority。
- `objectIndex`、`history`、`envelopes`、event metadata、`eventHeads`、
  receipt hints 和 TaskTrace 四张索引表是由 journal/checkpoint replay 重建的
  physical/query index，不是第二份事实源。
- TaskTrace profile cache 和 evidence cache 是 bounded、payload-free、可驱逐
  accelerator，当前限制为 32 entries、16 MiB；驱逐和重启只导致重算。
- Node catalog、nodeQueryReader、单次 TaskTrace event map、Work candidate/
  staging objects 和 View lease/pin 属于请求或 Work 私有状态。
- checkpoint 是认证后的 recovery projection，不保存 reducer 进程状态、reader、
  pin、delivery grant 或当前 authorization result。

## 正式 benchmark

正式命令：

```sh
go test ./engine -run '^$' -bench '^(BenchmarkTaskTraceProfile|BenchmarkTaskTraceScopeLookup|BenchmarkTaskTraceHistoricalChildren|BenchmarkTaskTraceSmallPage|BenchmarkR14AgentPrepareGrowth)' -benchmem -benchtime=1x -count=3 -cpu=1
```

正式样本在 Darwin/arm64 Apple M1 执行。下表保留三次样本范围；`B/op` 和
`allocs/op` 是累计分配，不是峰值 heap 或 RSS。

这些结果说明 Work 内的 warm reuse 可以显著减少 object reads 和 read bytes，但
candidate clone、record image、projection 和临时结果仍产生大量累计分配。大规模
fixture 逼近当前 record-count 边界，不能称作默认能力或峰值内存上限。

## 当前判断

R24 以“第一阶段内存、索引和 cache 基线完成”收口：

- TaskTrace bounded cache 的 warm scope/provenance 成本显著低于 cold projection，
  说明现有 cache 的加速方向成立。
- TaskTrace profile/index 的常驻结构会随历史规模增长；这些结构可由 durable
  history/checkpoint 重建，但当前没有对所有索引做 live eviction。
- Agent prepare 的 Work warm path 减少了重复 object reads，却没有消除大规模
  candidate/projection 的累计分配。
- `B/op`、`allocs/op`、`profile-bytes`、`record-bytes`、`state-raw-B` 和
  `read-B/op` 都不能直接替代 RSS、峰值 heap、page cache 或设备内存。
- observation 的 `RetainedEstimate` 只记账 cache 已有 retained estimate，也不
  覆盖整个 Engine heap。

本阶段不新增全局 index cache、增量 reducer 或强制 eviction。若需要真正的峰值
内存预算，下一阶段必须使用 runtime heap profile、明确并发数、冷/暖恢复和
checkpoint 生命周期，并单独记录 fixture 规模与配置；当前 benchmark 只提供
累计分配和结构容量证据。
