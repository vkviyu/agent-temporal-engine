# R16 Memory 领域容量基线验证

日期：2026-11-17。本阶段只建立 `memory` 纯领域 Store 的容量和 mutation
基线，不修改生产代码、主计划或其他工作区，也不提交 Git。benchmark 文件为
[`memory/memory_benchmark_test.go`](../../memory/memory_benchmark_test.go)。

## 范围和构造

- 新增六个 benchmark：`BenchmarkMemoryStoreApplyCommand`、
  `BenchmarkMemoryStoreGetAndSearch`、`BenchmarkMemoryStoreReusableMemoryFor`、
  `BenchmarkMemoryStoreAccessPolicy`、`BenchmarkMemoryStoreEncodeRestoreSnapshot`
  和 `BenchmarkMemoryStoreRetractSource`。
- 每个 benchmark 都运行 `small`、`medium`、`near_snapshot_limit` 三档。
- fixture 只使用公开 Store API：`PutCandidate`、`Validate`、`Promote`、
  `BuildExperiencePath`、`Snapshot`、`EncodeSnapshot` 和 `RestoreSnapshot`。
  benchmark 没有直接访问 Store 的 private maps。
- Memory 记录包含两个 source、evidence、applicability tags 和连续的
  transitive source chain；fixture 另外构造三个 ExperiencePath，后两个通过
  `DerivedFrom` 连接前一个 path。每条 path 只有一个 step 和一个 omitted node，
  用于保留小型 path 依赖图。
- fixture 根据实际 `EncodeSnapshot` raw bytes 增长。数组字段远低于
  `MaxItems=4096`，claim 远低于 `MaxClaimBytes=1 MiB`，记录数限制为
  `MaxSnapshotRecords-16` 以内；near 档目标约为 `MaxSnapshotBytes` 的
  7/8，编码失败时恢复到上一个合法快照并缩小 batch。
- 读 benchmark 始终使用同一只读 Store。`ApplyCommand` 和 `RetractSource`
  每次迭代先从固定 baseline raw 调用 `RestoreSnapshot`，不会累计上一次
  mutation 产生的版本、ban 或 successor。

## 计时前语义预检

每个三档子 benchmark 在 `ResetTimer` 前执行以下检查：

1. `EncodeSnapshot -> RestoreSnapshot -> EncodeSnapshot` 的 raw bytes 完全相等。
2. baseline 的 latest Memory、latest ExperiencePath 可 audit read，且
   `ReusableMemoryFor`、`ReusablePathFor` 均允许复用。
3. `RetractionUseBan` 后，旧 Memory/path ID 仍可 `Get`/`GetPath` 读取，
   但两者 reuse 均返回 `ErrNotEligible`；`AccessPolicy.Check` 对 audit
   允许、对 reuse 返回 `ErrUseDenied`。
4. `RetractionPrivacyErasure` 后，`AccessPolicy.Check` 对 audit 返回
   `ErrHistoryAccessDenied`。
5. baseline `AccessPolicy` 的 audit/reuse oracle 均通过，并以
   `DependencyClosure` 记录 dependency node 数。
